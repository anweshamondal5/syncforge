# Conflict-Free Replicated Data Types (CRDT) in SyncForge

## 1. Introduction to CRDTs in SyncForge

SyncForge implements real-time collaborative text editing using **Conflict-Free Replicated Data Types (CRDTs)**. Unlike centralized **Operational Transformation (OT)** systems (used in early Google Docs), which require a central authority to sequence operations and execute complex transformation functions ($T(op_1, op_2)$), CRDTs achieve **Strong Eventual Consistency (SEC)** deterministically across peer replicas without central coordination.

---

## 2. Mathematical Formalism & Invariants

A distributed system achieves Strong Eventual Consistency if:
1. **Eventual Delivery**: Every update generated by one replica is eventually delivered to all non-faulty replicas.
2. **Convergence**: Replicas that have received the same set of updates reach identical state, regardless of the order in which updates were received.

Mathematically, a State-based CRDT (CvRDT) forms a **bounded join-semilattice** $(\mathcal{S}, \sqcup)$ where:
- $\mathcal{S}$ is a partial order $\le$ of document states.
- The merge operator $\sqcup: \mathcal{S} \times \mathcal{S} \to \mathcal{S}$ computes the least upper bound (LUB).
- The merge operator satisfies:
  - **Commutativity**: $A \sqcup B = B \sqcup A$
  - **Associativity**: $(A \sqcup B) \sqcup C = A \sqcup (B \sqcup C)$
  - **Idempotence**: $A \sqcup A = A$

In Operation-based CRDTs (CmRDTs), concurrent operations commute ($op_1 \circ op_2 = op_2 \circ op_1$) given causal delivery.

## 3. Sequence CRDT: Yjs Internal Data Model

SyncForge utilizes the **Yjs sequence CRDT**, an optimized variation of the YATA algorithm (Yet Another Text Approach).

### A. The Item Struct
The document is represented as a doubly-linked list of immutable **Items**. Each item contains:
```typescript
interface Item {
  id: ID;              // Unique (client: number, clock: number)
  origin: ID | null;   // ID of the left item when this item was created
  left: Item | null;   // Current left neighbor in the local linked list
  right: Item | null;  // Current right neighbor in the local linked list
  rightOrigin: ID | null; // ID of the right item when this item was created
  parent: AbstractType;   // Parent XML Element or Text node
  content: Content;    // The actual inserted characters or embedded structure
  deleted: boolean;    // Tombstone flag for deleted content
  length: number;      // Length of the text chunk
}

interface ID {
  client: number;      // 53-bit random client identifier
  clock: number;       // Monotonically increasing Lamport sequence number
}
```

### B. Invariant Ordering & Conflict Resolution
When two clients concurrently insert text at the same relative position (e.g., between item $L$ and item $R$), both items reference $L$ as their `origin` and $R$ as their `rightOrigin`.

To deterministically place conflicting items $Item_A$ and $Item_B$:
1. If $Item_A.\text{origin} = Item_B.\text{origin}$, order by **Client ID**:
   $$\text{position}(Item_A) < \text{position}(Item_B) \iff Item_A.\text{client} < Item_B.\text{client}$$
2. Items never change their `origin` or `rightOrigin`. This ensures that even if updates arrive out-of-order or via different network paths, every replica reconstructs the exact same linked-list order.

```
       Initial State: [A] <----------------------------> [D]
                              (Concurrent Insert)
        Client 1 (ID 100): Inserts [B] with origin [A]
        Client 2 (ID 200): Inserts [C] with origin [A]

       Deterministic Resolution:
        Client 200 > Client 100  =>  [A] -> [B] -> [C] -> [D]
```

## 4. Deletions & The DeleteSet (DS)

In naive CRDT implementations, deleting text leaves behind memory-heavy tombstones. Yjs and SyncForge solve this with an optimized **DeleteSet**:
- When text is deleted, the item's `deleted` flag is set to `true`.
- The actual character payload (`content`) is garbage-collected to save memory.
- Deletions are encoded as compact ranges in a `DeleteSet`:
  $$\text{DeleteSet} = \{ \text{client} \to [(\text{clock}_{\text{start}}, \text{length}), \dots] \}$$
- A DeleteSet of 10,000 continuous character deletions occupies fewer than 30 bytes over the wire.

## 5. State Vectors & Delta Synchronization

Rather than exchanging full document snapshots, SyncForge uses **State Vectors** to compute exact minimal diffs.

### State Vector Representation
A State Vector records the highest contiguous Lamport clock received from every known client:
$$\text{StateVector} = \{ \text{client}_1: \text{clock}_1, \text{client}_2: \text{clock}_2, \dots, \text{client}_k: \text{clock}_k \}$$

### Two-Step Differential Handshake
```
Client A                                              Server / Client B
   │                                                         │
   │ 1. Encode local StateVector (SV_A)                      │
   ├─────────────── SyncStep1(SV_A) ────────────────────────>│
   │                                                         │ 2. Compute missing updates:
   │                                                         │    Diff = Updates in Doc_B
   │                                                         │           not covered by SV_A
   │                                                         │
   │<────────────── SyncStep2(Diff, SV_B) ───────────────────┤
   │ 3. Apply Diff to Doc_A                                  │
   │ 4. Compute missing updates in Doc_A                     │
   │    not covered by SV_B                                  │
   │                                                         │
   ├─────────────── SyncUpdate(Diff_A) ─────────────────────>│
   │                                                         │ 5. Apply Diff_A to Doc_B
   ▼                                                         ▼
[Replicas Converged to Identical State Vector: SV_A == SV_B == SV_Combined]
```

## 6. Mathematical Convergence Guarantees in SyncForge

| Property | Guarantee | Verification in SyncForge |
| :--- | :--- | :--- |
| **Commutativity** | Operations apply in any order with identical outcome. | Verified in `tests/distributed_chaos.test.ts` (Test 11 & 16: Out-of-order chunks). |
| **Associativity** | Grouping of updates into network packets does not change result. | Verified in `tests/distributed_chaos.test.ts` (Test 9: Micro-burst coalescing). |
| **Idempotency** | Duplicate delivery of updates produces zero side-effects. | Verified in `tests/crdt.test.ts` & `tests/distributed_chaos.test.ts` (Test 10). |
| **Monotonicity** | Document state advances strictly forward along Lamport clocks. | Verified in `packages/client/src/lib/sync/SyncForgeProvider.ts`. |
